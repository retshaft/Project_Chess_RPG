# ZCode 장기 목표 — 전투 판정 안정화와 다음 개발 단계 준비

작성일: 2026-09-09 / 메인: Codex / 대상: GLM-5.3-Flash

이 문서는 현재 C01 리뷰 수정 세션이 종료된 뒤 전달할 연속 작업 지시문이다. 실행 중인 세션에 전달된 상태가 아니며 자동 예약도 아니다. 현재 작업을 중복 실행하지 않는다. 재개할 때 메인이 기존 변경과 종료 결과를 확인하고 아래 후속 문서의 소유권을 작업서에 추가한다. 자동 호출의 깨끗한 워크트리 조건을 우회하거나 기존 변경을 초기화하지 않는다.

## 전달할 목표

당신의 장기 목표는 Checkmate RPG의 전투를 **플레이어가 결과를 이해하고 신뢰할 수 있는 상태**로 만들고, 다음 보상·저장·상태 작업을 곧바로 배정할 수 있을 만큼 조사와 재현 근거를 준비하는 것이다. 작업 시간을 채우거나 기능 개수를 늘리는 것이 목표가 아니다. 아래 과정을 우선순위대로 진행하고, 하나가 메인 검토에 막혀도 독립적으로 수행 가능한 다음 조사 작업을 계속하라.

명일방주를 의식한 수집·육성·편성·직군·재도전의 방향은 유지한다. 돌파 구조에 관한 제안 16은 보류다. 승급 AP 회복에 관한 제안 18은 조사 완료 자료를 재사용하며 수치·동작을 수정하지 않는다. 새로운 밸런스 규칙을 사용자 대신 결정하지 않는다.

## 시작 시 확인

1. AGENTS.md, Docs/Parallel/WORKFLOW.md, 배정된 Ready 작업서와 기존 인계서를 읽는다.
2. 현재 브랜치·워크트리·기준 커밋과 자신의 기존 변경을 확인한다. 현재 C01 작업은 `codex/zcode/c01-grace-review-fixes`, `.worktrees/zcode-c01-grace-review-fixes`, 시작 기준 `01a5417e196cfd6ed1fb451a2df0d198fab3a23d`다. 다른 경로에서 이 작업을 그대로 시작하지 않는다.
3. 현재 진행 중인 C01 결과를 처음부터 다시 작성하지 않는다. 수정 완료·미완료·검증 대기를 나눈 뒤 남은 단계부터 이어간다.
4. 코드 편집 권한은 `Docs/Parallel/Tasks/c01-attack-grace-review-fixes.md`의 정확한 파일 목록으로 제한한다. 아래 보상·상태·AI 관련 단계는 조사·재현 설계이며 해당 런타임 파일의 편집 권한이 아니다.

## 1단계 — C01 리뷰 지적 해결

기존 구현과 테스트를 읽고 다음을 끝까지 처리하라.

- 실전과 예측의 공격 규칙 차이를 제거한다. 기물 종류·팀 방향·사거리 정보는 같은 의미로 사용하고 위치·점유·상태는 각자의 런타임에서 조회한다. 예측이 실제 오브젝트를 이동시키거나 이벤트를 발행하면 안 된다.
- 정상 이동 이후 강제 이동된 대상의 이전 기록을 무효화한다. 공격자 강제 이동도 놓치지 않는다. 실패한 이동이나 위치가 그대로인 처리까지 불필요하게 정상 공격을 취소하지 않는지 확인한다.
- 공격 접수 전에 사거리가 유효했는지 전체 호출 경로에서 확인한다. UI만 선검사하는 구조라면 우회 접수 재현을 만들고 허용 범위에서 최소 수정한다.
- 유예는 일반 공격과 정상 이동의 정해진 범위에만 적용한다. 대상 ID와 피해 횟수를 보존하고, 광역·특수 능력에 자동 확대하지 않는다.
- 동일 틱의 접수/이동 순서, 연속 이동, 사망, 취소, 인터럽트, 공격자 이동을 확인한다. 틱만으로 구별할 수 없는 경우에는 근거와 실제 지원하는 경계를 적고 임의로 완전 지원이라 주장하지 않는다.

완료 기준: 각 리뷰 지적에 해결 코드와 회귀 근거 또는 명확한 차단 원인이 연결되어 있다. 필요한 공통 상태가 클론·스냅샷·재생에서 보존된다. 수식·AP 비용·유예 시험값을 동시에 튜닝하지 않는다.

## 2단계 — 판정 테스트와 플레이 확인 절차 완성

기존 테스트를 단순 복제하지 말고 실제 실패를 잡는 테스트를 우선 작성하라.

- 정상 사거리 판정과 유예 판정 각각에서 실전 규칙과 PredictionBattleContext 결과를 비교한다. 비숍 비대각선, 룩 대각선, 나이트 이동형 공격, 폰 방향과 양 팀을 포함한다.
- 정상 이동→강제 이동, 공격자 강제 이동, 반복 이동, 유예 마지막 틱/다음 틱, 설정 0, 이동 이후 새 공격을 검증한다.
- 다른 유닛이 이전 칸에 진입해도 그 유닛이 맞지 않는지, 대상 사망·공격 취소 뒤 추가 피해가 없는지 리졸버/파이프라인 경로를 통해 검증한다.
- 실제 프로젝트의 BasicAttackAbility 사용 유닛과 레거시 AttackAction 사용 유닛을 구분한다. 이 기능이 사용자에게 문제가 된 실제 입력 경로에 적용되는지 설명하라. 적용되지 않으면 해결됐다고 결론내리지 말고 최소 후속 변경안을 작성한다.
- 정상 이동을 유도하는 Play 절차를 작성한다. 넉백을 이용해 정상 이동 유예를 검증하지 않는다. 테스트용 유닛·입력 순서·관찰 시점·기대 결과를 구체적으로 적는다.

Unity 실행은 현재 자동 배정에서 허용하지 않는다. 가능한 정적 점검과 테스트 작성은 계속하고 실제 컴파일·Test Runner·Play Mode 실행은 메인에게 남긴다. 과거 67/68 기록을 새 결과로 사용하지 말라.

## 3단계 — 보상·저장 경로의 다음 작업 준비

코드는 읽되 수정하지 않는다. 기존 아웃게임 감사 자료가 있으면 재사용하고 현재 코드와 다른 부분만 갱신하라.

- 결과 표시→보상 계산→재화/유닛/해금 반영→저장→복귀의 호출 흐름을 추적한다.
- 결과 화면 재표시, 동일 전투의 중복 콜백, 지급 도중 실패, 저장 재시도, 앱 재실행을 구분한다. 단순 bool 하나로 모든 중복·유실이 해결된다고 제안하지 않는다.
- 최초 클리어와 반복 클리어 보상의 현재 구분을 확인한다. 새 전투의 정당한 반복 보상을 차단하지 않는 식별 기준을 제안한다.
- 기존 저장 형식, 실패 시 동작, 손상 파일 처리, 백업 유무를 확인한다. 기존 세이브를 보존하면서 가능한 최소 수정안을 제시한다.
- 보상 중복 방지와 저장 복구를 따로 검토할 수 있도록 두 개의 후속 작업으로 나누고 정확한 수정 후보 파일·예상 회귀 테스트·선행 조건을 적는다.

산출물: `Docs/Parallel/Handoffs/long-goal-reward-save-audit.md`.
완료 기준: 문제마다 재현 가능한 경로 또는 아직 확인이 필요한 가설 표시가 있고, 메인이 바로 허용 파일을 확정할 수 있다.

## 4단계 — 상태 효과 정합성의 다음 작업 준비

코드·GDD·기존 M3 감사/인계서를 비교하되 상태 규칙은 변경하지 않는다.

- 적용·스택·갱신·교체·만료·정화 시 실제 Runtime과 컴포넌트/UI가 같은 상태를 읽는지 확인한다.
- 승급 상태 제거 경로를 확인하되 AP 회복이나 돌파를 변경하지 않는다.
- Poison 실패 사례의 기대값과 실제 프로세서 수식, 데이터 배율을 대조한다. 테스트가 틀렸는지 구현이 틀렸는지 확정할 근거가 없다면 둘을 임의로 맞추지 않는다.
- 상태 제거 후 이동/공격 제한이 남는 경우, 사망 후 DOT, 갱신과 만료가 같은 틱인 경우를 조사한다.
- 가장 작은 재현 사례와 기존 전투 경로를 재사용하는 수정 후보를 작성한다.

산출물: `Docs/Parallel/Handoffs/long-goal-status-audit.md`.
완료 기준: 확인된 결함, 문서 충돌, 미검증 가설이 분리되어 있으며 각 항목에 파일·호출 흐름·검증 절차가 있다.

## 5단계 — 킹 추격과 전투 난이도의 시험 설계

AI·데이터·씬을 수정하지 않는다. 사용자가 확인한 적 MaxAP 100을 미해결 버그로 반복 등록하지 않는다.

- 적 이동 AP 20, 실제 이동 주기, AP 회복과 입찰·평가 주기 사이의 관계를 읽는다.
- 불필요한 왕복/도주와 유효한 전술적 후퇴를 구분하는 사례를 만든다.
- 전체 전투 시간, 마지막 적 처리 시간, 접수된 공격 중 사거리 실패 비율을 따로 측정하는 절차를 설계한다.
- 같은 배치·편성에서 유예 0과 시험값을 비교한다. 실제로 실행하지 않은 숫자는 만들어내지 않는다.
- 기존 StageData와 에디터 도구로 가능한 대표 적 배치를 제안한다. 킹을 무조건 정지시키거나 새 AI 프레임워크를 설계하지 않는다.
- 안전한 위치에서의 일방 공격, 킹 직행, 무료 공격/AP 생산, 회복을 기다리는 무한 대기의 검증 시나리오를 적는다.

산출물: `Docs/Parallel/Handoffs/long-goal-king-chase-test-plan.md`.
완료 기준: 초보·일반·최적화 플레이어가 각각 무엇을 시도할지와 관찰 지표가 구체적이며, 플레이테스트 결과 없이 밸런스를 단정하지 않는다.

## 6단계 — 최종 자체 리뷰와 인계

- 변경한 C01 파일을 다시 읽고 별도 전투 경로, 유령 점유, 실제 상태를 참조하는 예측, 반복 경로의 불필요한 할당, 직렬화 호환성 문제가 없는지 확인한다.
- 해결에 필요한 코드만 유지한다. 원래 존재하던 타인의 변경을 되돌리지 않는다.
- C01 인계서에 작업 중 추가한 테스트, 실제 실행한 검증, 실행하지 못한 검증을 구분한다.
- 각 후속 보고서는 단일 결론과 실행 가능한 다음 작업 중심으로 작성한다. 분량을 채우기 위해 GDD를 재서술하지 않는다.
- `Docs/Parallel/Handoffs/long-goal-summary.md`에 완료/검토 대기/사용자 결정/환경 차단을 요약하고 다음 Ready 후보를 우선순위대로 최대 5개 제시한다.

## 연속 작업 방식

- 한 단계가 끝나면 독립적으로 가능한 다음 단계로 이동한다. 작은 단계마다 사용자 승인을 반복 요청하지 않는다.
- 코드 수정 범위나 미확정 규칙에 막히면 해당 부분만 보고서에 남기고 다음 독립 조사로 진행한다. 모든 작업을 함께 중단하지 않는다.
- 각 단계 완료 시 요약 파일을 갱신하고 가능한 세션 진행 메시지에 현재 단계·완료한 결과·다음 행동을 짧게 적는다. 백그라운드 호출은 메시지가 UI에 실시간 표시되지 않을 수 있으므로 파일에도 기록한다.
- Git 커밋·병합·리베이스·원본 반영, Unity 실행, 다른 AI 호출, 권한 우회는 하지 않는다. 메인이 수행한다.
- 자동 호출 재개 시 메인은 C01 기존 허용 목록에 이 문서의 후속 보고서 4개를 정확히 추가해야 한다. 에이전트가 자기 권한을 확대하지 않는다.
- 목표는 1~6단계의 유의미한 산출물 완성이다. 시간이 남아도 새 기능이나 다음 마일스톤 구현으로 확대하지 않는다. 완료되면 종료한다.
- 인증·사용량 한도·권한 차단·실행 제한에 도달하면 변경과 재개 지점을 보존한다. 무한 재시도, 대기 반복, 계획 재작성으로 시간을 채우지 않는다.

## 실행상 한계

현재 연결기는 설치된 ZCode에서 거부된 `--max-turns` 옵션을 제거하고 목표를 프롬프트로 전달한다. 이 문서 작성만으로 ZCode의 실제 `/goal` 기능이나 밤새 자동 재개가 활성화되지는 않는다. 앱에서 목표로 사용할 때는 위 지시문을 지원되는 Goal 입력에 전달하고, 자동 호출은 별도 Ready 작업서와 실행 제한에 맞춰 메인이 배정한다.
