# 회의 후 개발 명령서

기준일: 2026-09-08. 작성: Codex. 대상: ZCode / GLM-5.3-Flash 중심, 필요시 Gemini 분담.

## 사용자 결정과 실행 상태

- 명일방주를 의식한 수집·육성·편성·직군·반복 도전의 방향을 유지한다. 이를 제거한 체스 퍼즐로 축소하지 않는다.
- 제안 16은 **보류**다. 일반적인 서브컬처 게임의 돌파와 유사한 시스템이라는 사용자 의도를 존중한다. 중복 획득에 따른 핵심 능력 해금 구조를 변경·제거하지 않는다.
- 제안 18은 **조사만 수행**한다. 승급 AP 전량 회복을 삭제하거나 다른 수치로 교체할 권한은 없다.
- 나머지 제안은 유지한다. 이는 목표의 유지이며, 아직 정하지 않은 수치나 새 규칙을 AI가 확정하라는 의미가 아니다.
- 이 문서는 개발 범위와 순서를 정한 총괄 명령서다. 현재 개별 작업은 **Draft / 미배정**이며 실제 AI 호출, 자동 실행, Git 통합을 하지 않았다.
- 기존 `GLM_TASK_QUEUE.md`와 충돌하는 우선순위·범위는 이 문서를 따른다. 기존 산출물을 폐기하거나 같은 조사를 중복 수행하지 않는다.

## 배정 전 메인 개발자가 할 일

1. 현재 변경과 인계서를 검토한다. 적 데이터 8개, OutgameScene, Recovery 씬 및 기존 M2/M3 결과를 보존한다.
2. `AttackGraceRules.cs`, `IReadOnlyUnitRuntimeState.cs`, `UnitRuntimeState.cs`, `SimulationRuntime.cs`에 미커밋 피격 유예 관련 변경이 있다. 작성자와 진행 범위를 확인하고 재사용 여부를 판단한다. 별도 유예 시스템을 새로 만들거나 덮어쓰지 않는다.
3. 배정할 단일 작업마다 `TASK_TEMPLATE.md`에 정확한 허용 파일과 `.meta`, 테스트·인계서 경로, 실제 기준 SHA, 전용 브랜치와 절대 워크트리 경로를 채운다. 아래의 ‘검토 대상’은 편집 허용 목록이 아니다.
4. 공통 변경과 작업서를 기준에 포함한 뒤 `Ready`로 전환한다. 메인 검증 전 결과는 `Review`이며 구현 완료 보고만으로 `Verified` 처리하지 않는다.
5. M2/M3 기존 결과의 컴파일·Unity 테스트·필요한 Play Mode 검증을 먼저 정리한다. 과거 빌드 기록을 현재 전체 변경의 통과 근거로 사용하지 않는다.

## D18 — 승급 AP 전량 회복의 근거 확인

**목적:** 사용자의 기억과 현재 문서·구현 사이의 차이를 확인한다. 변경 방향을 미리 정하지 않는다.

**현재 확인한 증거:**

- `Game Proposal/[Project_ Checkmate RPG] 마스터 기획서 (Master GDD) - Part 3_ 자원 경제(AP) 및 세부 직군 명세 (개별 해설본).md` 35행에 “AP를 100% 회복한 상태로 즉시 행동” 문구가 있다.
- `Assets/Scripts/Units/UnitBrain.cs` 414~422행은 아군 승급 시 `APManager.Instance.AddAP(APManager.Instance.MaxAP, APSource.Bonus)`를 호출한다. 개인 AP가 아니라 공용 AP 관리자에 최대치만큼 보너스를 전달한다.
- 해당 호출의 현재 Git blame은 `acb9ddba`를 가리킨다. 백업 커밋에 포함됐다는 사실만으로 최초 기획자나 사용자 승인을 입증할 수 없다.

**명령:** GDD 변경 이력, 해당 커밋 이전 코드, AP 상한 처리, 승급 반복·재진입 가능성, 적 승급 처리와 관련 테스트를 읽어라. 문서 표현, 실제 회복 대상·양·시점, 근거를 찾지 못한 부분을 나눠 보고하라. 원래 사용자가 요청했다는 추측을 쓰지 말라. 회복 유지/제거/대체는 영향만 비교하고 코드와 GDD를 수정하지 말라.

**산출물:** `Docs/Parallel/Handoffs/D18-promotion-ap-audit.md`만 작성하도록 개별 작업서에 지정한다.

**완료 조건:** 근거 경로·행·커밋과 확인 불가 항목이 있고, 사용자에게 결정받아야 할 실제 규칙이 명확하다. 조사 완료는 회복 규칙 승인과 다르다.

**플레이 확인:** 이후 메인 실행권 아래 승급 직전·직후 공용 AP를 비교한다. 미실행이면 정적 코드 확인으로만 보고한다.

## C01 — 이동 후 피격 유예

**목적:** 이동 AP가 낮은 적을 계속 쫓다가 유효하게 시작한 공격이 반복해서 실패하는 문제를 줄인다.

**명령 / 범위:** 기존 근접·원거리 구분 필드를 찾아 사용하라. 사거리나 이름으로 타입을 추정하거나 새 타입 체계를 만들지 말라. 진행 중인 유예 코드와 접수→사전검증→해석→뮤테이션→예측·리플레이 흐름을 먼저 대조하라.

- 이동 전에 유효하게 시작되어 대상이 고정된 공격만 유예 후보로 삼는다. 새로 시작한 공격이 과거 위치를 공격해서 맞히게 하지 않는다.
- 현재 위치의 정상 판정을 우선하고, 대상의 정상 이동 때문에 사거리 판정이 실패한 경우에만 직전 이동 위치를 검사한다. 과거 위치 여러 개를 누적하지 않는다.
- 근접·원거리 유예를 각각 설정 가능한 논리 틱 값으로 둔다. 0은 기존 판정이다. 기본 지속시간은 미확정이며 테스트 후보와 최종값을 구분한다.
- 원거리 발사 전/후, 투사체·추적 여부는 실제 구현을 확인하여 기존 규칙을 유지한다. 이 작업을 위해 새 투사체 시스템을 추가하지 않는다.
- 대상 ID로 한 번만 피해를 준다. 이전 칸에 들어온 다른 유닛, 취소된 공격, 죽은 대상에 피해를 주지 않는다. 은신·무적 등 다른 유효성 규칙을 우회하지 않는다.
- 양 팀의 일반 공격·정상 이동에 대칭 적용한다. 광역·지정 칸 공격·특수 스킬·넉백·당기기·순간이동은 자동 편입하지 않는다.
- 유령 콜라이더나 추가 점유 유닛을 만들지 않는다. 논리 이동 시점과 화면 이동 완료 시점을 구분하고 동일 틱 내 공격 접수·이동 순서도 명시한다.
- 추가 상태는 복제·스냅샷·재생에 필요한 경로까지 유지한다. 실제 전투·예측·리플레이가 같은 규칙을 사용한다.

**완료 조건:** 유예 안/밖, 설정 0, 이동 후 새 공격, 연속 이동, 동일 틱 순서, 대상 교체·사망·취소, 강제 이동 제외를 회귀 테스트한다. 예측·실제·리플레이 결과가 일치하고 컴파일 및 관련 테스트가 통과한다.

**플레이 확인:** 이동 AP 20인 킹 추격, 일반 이동 적, 아군 이동 피격을 비교한다. 공격 실패율·마지막 적 처리 시간·이미 멀어진 적이 맞아 보이는 혼란을 기록한다. AP 비용을 동시에 바꾸지 않는다.

## R01 — 보상과 저장 안정화

**목적:** 결과 화면 재표시나 저장 실패로 보상이 중복되거나 진행이 사라지는 문제를 방지한다.

**범위:** `BattleResultUI`의 결과 표시와 보상 지급 호출, `SaveManager`, 진행 데이터의 실제 소유권을 읽는다. R01a 보상 중복 방지와 R01b 저장 복구를 각각 검토 가능한 변경으로 나눈다. UI를 열 때마다 지급하지 않게 하고, 동일 전투 결과의 식별·지급 기록·저장이 어떻게 함께 유지되는지 설계한다. 단순 메모리 bool만으로 재실행 시 중복 지급까지 해결됐다고 보고하지 않는다.

저장은 기존 형식 호환을 유지하고 임시 파일·백업·복구 등 최소한의 안전한 경로를 적용한다. 읽기 실패를 즉시 새 저장으로 덮어쓰지 않는다. 클라우드 저장이나 완전한 부정행위 방지 체계를 추가하지 않는다.

**완료 조건:** 동일 결과 반복 표시, 정상 재도전의 새 보상, 지급 중 실패 후 재시도, 저장 중단·손상·백업 복구, 기존 세이브 로드를 검증한다. 중복 지급과 보상 유실을 함께 확인한다.

**플레이 확인:** 승리→결과 재열기→복귀→재실행 후 재화·유닛·해금이 기대값과 일치하는지 확인한다. 저장 실패 안내가 사용자가 다음 행동을 선택할 수 있게 하는지 본다.

## C02 — 상태 정합성과 대표 콤보

**목적:** 일반 입력으로 넉백/Splat을 사용하고 상태 적용·제거·예측·UI가 같은 결과를 보여주게 한다.

**범위:** 먼저 상태 제거 경로와 Runtime 상태의 일치를 검증하고 재현된 결함을 고친다. 이후 기존 능력 데이터·해석·뮤테이션으로 대표 콤보를 연결한다. M2 에디터 도구와 M3 테스트를 재사용하되 디버그 이벤트 후처리가 일반 능력 및 예측 완성을 뜻한다고 가정하지 않는다. 승급 시 상태 제거 검증이 18번 AP 규칙 변경으로 번지지 않게 한다.

**완료 조건:** 적용·갱신·교체·만료·정화가 실제 행동 제한 및 UI와 일치한다. 일반 스킬 입력으로 힘−실효무게와 기존 Splat 규칙이 적용되고, 예측과 실제 피해·위치가 일치한다. 기존 전투 경로 밖에서 피해를 직접 추가하지 않는다.

**플레이 확인:** 예측을 보고 대상과 충돌 상대를 선택할 수 있는지, 제거된 상태가 남아서 행동을 막지 않는지 확인한다.

## E01 — 추격, 난이도, AI와 인카운터

**목적:** 전투가 쉬운 문제와 마지막 킹을 쫓는 지루함을 분리한다.

**범위:** C01 적용 후 이동 쿨타임의 설계값과 실제 적용 여부, 킹 도주·왕복, AP 비용과 회복, AI 평가를 측정한다. 의도된 쿨타임의 누락은 수정 후보지만 새 쿨타임이나 비용 인상은 실험값으로 제시한다. 킹을 무조건 정지시키거나 승리 조건을 바꾸지 않는다. 기존 StageData·AI 스타일·에디터 도구로 역할이 다른 대표 적 배치를 구성한다. 깊은 탐색 AI나 새 웨이브 프레임워크를 만들지 않는다.

**완료 조건:** 전체 전투 시간과 마지막 적 처리 시간을 따로 기록하고, 수정 전후 같은 편성·배치로 비교한다. 안전지대 일방 공격, 무한 도주, 반복 왕복, 킹 직행, 무료 공격·회복 대기 악용의 재현 또는 미재현 근거를 제출한다.

**플레이 확인:** 초보는 적 역할을 읽을 수 있는가, 일반 플레이어는 배치 변경으로 개선되는가, 숙련자는 한 전략으로 모든 배치를 무력화하는가를 확인한다.

## G01 — 편성·육성·재도전과 파밍

**목적:** 전투 외 성장과 편성 변경이 다음 도전에서 의미를 갖게 한다.

**범위:** 기존 캐릭터 중 역할이 구분되는 대표 편성을 선정하고 덱→출격→승패→보상→편성/육성 변경→재도전을 연결한다. 첫 클리어와 반복 보상의 현재 구현·누락을 구분하고 기존 보상 데이터로 가능한 범위를 우선한다. 파밍·돌파를 제거하거나 성장 수치를 임의 변경하지 않는다. 새 보상량·성장 곡선은 결정 항목으로 남긴다.

**완료 조건:** 저장 후 재실행해도 편성과 성장 결과가 유지되고, 실패 후 복구 불가능한 진행 막힘이 없다. 첫 클리어 보상은 중복되지 않고 반복 클리어 보상은 정해진 규칙대로 지급된다.

**플레이 확인:** 패배한 사용자가 무엇을 바꿔 재도전할지 설명할 수 있는지, 반복 플레이가 보상만을 위한 무의미한 작업인지 관찰한다.

## B01 — 직군·성장 선택의 균형

**목적:** 효과 개수를 늘리기보다 편성과 전투 선택에 차이를 만든다.

**범위:** 물리 콤보 안정화 뒤 기존 원소 연계를 순차 검증한다. 빙결 유지/쇄빙, 제어형 편성 유무, 무료 공격/AP 생산, 공명 AP 할인 중첩, 칙령의 용량·효과 조합을 비교한다. 공명 할인 검토를 핑계로 보류된 16번 돌파 구조를 변경하지 않는다. 기존 공식·최솟값·중첩 순서를 확인하고 미정 규칙은 제안과 구현을 분리한다.

**완료 조건:** 각 선택이 유리한 상황과 불리한 상황을 재현 가능한 편성·적 배치로 제시한다. 비용 0/음수, 할인 중첩, 무한 자원, 제어 필수화, 단일 칙령·빌드 독점 여부를 검증한다. 확정된 결함 수정과 미확정 밸런스 제안을 구분한다.

**플레이 확인:** 최적화 플레이어도 적과 상황에 따라 선택을 바꾸는가를 본다. 능력을 사용하지 않는 선택에도 이유가 있는지 확인한다.

## U01 — 전투 정보 전달

**목적:** 공격 실패와 킹 위협을 플레이어가 이해하고 대응할 수 있게 한다.

**범위:** 기존 실패 사유·예측·이벤트를 사용해 사거리 이탈, 자원 부족, 상태 제한 등 행동에 필요한 정보를 표시한다. 매 프레임 전체 전투를 재검사하는 UI를 추가하지 않는다. 유예 기간 표시가 필요하면 최소한으로 적용하며 모든 내부 수치를 노출하지 않는다.

**완료 조건:** 표시 원인과 실제 해석 원인이 일치하고 취소·대상 사망·연속 실패에도 메시지가 남거나 과다 반복되지 않는다.

**플레이 확인:** 처음 하는 사용자가 공격이 실패한 이유와 다음 행동을 별도 설명 없이 말할 수 있는지 확인한다.

## X01 — 전술 감속/일시정지 비교 실험

**목적:** 정보 이해를 돕는지, 기다림과 조작 부담을 늘리는지 확인한다.

**범위:** 앞선 판정·UI 개선 이후에도 판단 시간이 부족한지 먼저 관찰한다. 필요할 때 기존 시간 제어를 활용한 최소 실험을 설계한다. 실시간/감속/정지를 같은 전투로 비교하며 영구 채택을 전제하지 않는다. 틱·AI AP 회복·상태 시간·입력 예약의 일관성을 확인한다.

**완료 조건:** 이해도, 전투 소요 시간, 정지 반복 횟수와 시간 제어 악용을 비교해 채택 또는 미채택 근거를 제출한다.

**플레이 확인:** 생각할 시간이 늘어 더 좋은 선택을 하는지, 매 행동마다 정지하는 노동이 되는지 확인한다.

## S01 — 후순위 능력의 범위 관리

**목적:** 운송·복제·소환(영구 사망 원칙, 부활 시스템 배제)의 기획은 보존하면서 현재 완성도를 먼저 확보한다.

**범위:** 기존 구현 유무와 대상 ID·점유·사망·보상·저장·예측에 대한 의존성만 정리한다. 새 런타임 구현, 능력 삭제, 대규모 구조 교체는 하지 않는다. (※ 전투 중 부활은 체스 룰에 따라 영구 배제)

**완료 조건:** 각 능력을 시작하기 위한 선행 조건과 최소 검증 시나리오가 있다.

**향후 플레이 확인:** 복제 보상 중복, 소환 유닛 처리 후 킹 승패, 운송 중 점유 충돌 등 핵심 사례를 이후 작업서에 인계한다.

## GLM 전달용 공통 명령

배정 시 아래 문구에 메인이 확정한 Ready 작업서 경로를 붙인다. 현재 이 문구를 실행하거나 전송하지 않는다.

> 지정된 단일 작업서를 목표로 조사→허용 범위 수정→검증→인계까지 수행하라. 먼저 AGENTS.md, WORKFLOW.md, 작업서를 읽고 워크트리·브랜치·기준 SHA·허용 파일을 확인하라. 기존 구현과 진행 중 변경을 재사용하고 계획만 제출한 채 끝내지 말라. 보류된 16번은 건드리지 말고, 18번은 조사 보고 외 변경하지 말라. 확정되지 않은 수치·규칙은 임의 결정하지 말라. 작업 범위 밖 수정이나 공통 API 변경이 필요하면 최소 변경안과 차단 사유를 인계하고 해당 부분은 대기하라. 다른 작업으로 자동 확대하지 말라. Unity 검증은 실행권을 얻은 지정 담당만 수행하며 미실행을 통과로 보고하지 말라. 인계서에 변경 파일, 현재 동작과 기대 동작, 수행한 테스트 결과, 미검증 항목, 사용자가 확인할 최소 절차를 기록하라.

Goal 기능을 사용할 경우에도 목표는 Ready 작업 한 건으로 제한한다. 실제 CLI 지원 옵션을 확인하고 설정하며, 무한 재시도나 다음 Draft 작업의 자동 시작을 허용하지 않는다. GLM의 한국 시간 00:00~10:00 사용 여유는 추후 사용자가 자동 실행을 요청할 때 스케줄에 반영한다. 이 문서는 예약을 생성하지 않는다.
