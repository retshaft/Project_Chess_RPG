## 결론 요약

1. **GDD에 근거가 있다.** "AP를 100% 회복한 상태로 즉시 행동" 문구는 GDD Part 3 §2.2(35행)에 있고, Git 이력상 **최초 커밋(9189a4d, 2026-05-06)부터 존재**했다. 코드는 그로부터 약 3개월 뒤 백업 커밋 acb9ddba(2026-08-09)에서 승급 시스템 전체와 함께 들어왔다. 즉 "문서가 먼저, 코드가 나중"이다.
2. **구현은 "아군 공용 AP 풀을 최대치까지 채우기"이다.** 개인 AP가 아니라 `APManager`(아군 전체 공용 풀, 상한 100)에 `AddAP(MaxAP, Bonus)`를 1회 호출하며, AddAP 내부 클램프(`Mathf.Min`) 때문에 상한을 넘어 누적되지 않는다. 시점은 승급 대기(3초) 종료 후 변신 완료 순간 1회다.
3. **그러나 확인 불가/미결 항목이 실제로 존재한다.** (a) 사용자가 이 규칙을 직접 요청·승인했다는 기록은 저장소 어디에도 없고, (b) GDD 문장의 주어가 모호해 "승급 유닛이 즉시 행동 가능한 상태"라는 대안 독해가 가능하며, (c) 적 폰 승급 시에는 적 팀 풀 회복이 없고, (d) 전령(전령 폰)은 재승급 시 AP 전량 회복이 반복되는 구조적 경로가 열려 있다. 이 4가지가 아래 §9의 사용자 결정 사항이다.

## 4. AP 상한 처리

- 아군 풀: `APManager` 싱글턴. `_maxAP = 100` 기본(`APManager.cs:22`), Awake에서 `CurrentAP = Clamp(initial, 0, max)`(`:59-60`). `AddAP`는 `Mathf.Min(_maxAP, CurrentAP + amount)`로 **상한 초과 누적이 원천적으로 불가능**(`:123`). `SetMaxAP`는 정의만 있고 호출부 0건(전수 grep) — 상한은 사실상 고정 100(M1 Play Mode에서 MaxAP=100 확인된 바와 일치).
- 적 풀: **`AITeamCommander`의 별도 풀**. `StageData.MaxEnemyAP`(미설정 시 100), `EnemyAPRegen`, `InitialEnemyAP`로 구성되고 회복도 자체 `Mathf.Min` 클램프(`AITeamCommander.cs:25-38, 103`). 적은 `APManager`를 쓰지 않는다.
- 전투 간 초기화: 전투 시작 시 `APManager.ResetToInitialAP()`(`BattleManager.cs:252-254`) — 승급 AP 보너스가 다음 전투로 이월되지 않는다.

## 5. 승급 반복·재진입 가능성

- **일반 폰(전령 제외)**: 승급 후 PieceType이 록/나이트/비숍/퀸/킹으로 바뀌므로 트리거 조건(`PieceType == Pawn`)을 다시 통과할 수 없다. 전투당 1회.
- **전령(Herald)**: 승급 대상이 **Pawn**(`PromotionRegistry.cs:33`)이라 변신 후에도 PieceType이 Pawn으로 남고, Subclass도 유지되며(`UnitBrain.cs:375`), 완료 시 `IsPromoting = false`로 복원된다(`:424`). 따라서 **승급 행에 다시 도달하면 재승급 → 스탯 ×1.5 중첩 + 공용 풀 전량 회복이 반복되는 구조적 경로가 열려 있다.** 단, 실전 발생 조건은 까다롭다: (a) 트리거는 자기 팀 기준 승급 행 한 방향만 본다(`MovementComponent.cs:335`) — GDD 59행의 "아군 진영 끝 재승급"은 미구현, (b) 트리거는 일반 이동(`MoveCoroutine`) 완료 시에만 발동하고 넉백 착지는 트리거가 아니다(`MovementComponent.cs:193, 208` 호출부), (c) 승급 후 최전행에서 전진 전용 이동 패턴으로 재도달이 가능한지는 이동 패턴·넉백 방향 조합에 달려 있다. → **구조적으로 가능, 실전 발생 여부는 Play 실측 필요(§12).**
- **재진입(스테이지 재도전)**: 승급 데이터는 런타임 생성 ScriptableObject로 저장되지 않고(`UnitBrain.cs:372`), AP도 전투 시작 시 초기화되므로(§4) **전투 간 누적 경로는 없다.**

## 6. 적 승급 처리

- 트리거는 양 팀 대칭이다: 적 폰은 y=0 도달 시 승급(`MovementComponent.cs:334-336`). 실제 적 폰 에셋이 `PieceType: 0`(=Pawn)이므로(`Assets/Resources/Units/Enemies/Enemy_BlackPawn.asset:19`) 적 승급 경로는 살아 있다. Subclass가 None(0)이라 승급 대상은 기본값 퀸(`PromotionRegistry.cs:35`).
- 스탯 ×1.5·상태 제거는 적도 동일하게 받는다. 그러나 **AP 전량 회복은 아군만이다**(`UnitBrain.cs:419`). 적 승급 시 적 팀 풀(`AITeamCommander`)은 회복되지 않는다.
- GDD는 팀 구분 없이 "AP를 100% 회복"이라만 표기해(§1) **적 승급 시 적 풀 회복 여부는 문서 어디에도 정의되어 있지 않다.** 참고로 GDD §1.1의 "중앙의 AP"는 단일 풀을 전제하나, 실제 구현은 아군(`APManager`)·적(`AITeamCommander`) 이중 풀이다 — 이 이중화 자체도 GDD에 명시 문구가 없는 구현 현실이다.

## 7. 관련 테스트

- `Assets/Scripts/Testing/EditModeTests/`에서 Promotion·APManager 관련 테스트 **0건**(전수 grep). `BattleTestBootstrapper.cs:281-292`는 전투 검증용 샌드박스에 APManager를 생성할 뿐 승급 AP 규칙을 검증하지 않는다.
- 즉 승급 AP 회복은 **회귀 테스트로 보호되지 않는 규칙**이다. 규칙을 유지하기로 결정되더라도 "아군 승급 시 풀이 상한까지 채워지는가 / 적 승급 시 변동 없는가 / 상한 초과가 아닌가"에 대한 EditMode 테스트가 없는 상태다.

## 8. 확인 불가 항목 (근거를 찾지 못한 부분)

1. **GDD 원문의 작성 경위**: Git 이력이 최초 커밋(9189a4d)까지만 존재한다. 그 이전 작성 과정, 작성자, 검토 기록은 이 저장소에서 확인할 수 없다.
2. **acb9ddba 이전의 작업 버전**: 해당 커밋은 대량 백업("Backup current state before M0 cleanup")이라, AP 회복 코드가 어떤 작업 흐름에서 작성됐는지 커밋 단위 추적이 불가능하다. 커밋 작성자 필드는 사용자 Git 신원(황동윤)이지만 백업 성격상 특정 설계 결정의 승인 증거로 쓸 수 없다(명령서도 동일하게 지적).
3. **사용자의 직접 요청·승인 기록**: "승급 시 AP 전량 회복"을 사용자가 요청했거나 승인했다는 기록을 이 저장소에서 찾지 못했다. 유사한 추측도 하지 않았다.
4. **"즉시 행동"의 기획 의미**: 문장만으로 "즉시 행동 예약"인지 "자원 충전 상태"인지 확정할 수 없다. 현 구현은 후자(풀 충전 + 쿨타임 리셋, §2)다.
5. **적 폰 승급의 실전 발생 빈도**: 적 AI가 폰을 승급 행까지 전진시키는지는 AI 평가 로직 측정 문제(E01 범위)로, 정적 분석만으로는 확정하지 않았다.

## 10. 유지 / 제거 / 대체 영향 비교 (어떤 선택도 하지 않음)

| 방향 | 영향 |
|---|---|
| **유지** | GDD(§1 독해 기준)와 구현이 일치하고, 폰 육성·승급의 보상 체감이 커서 수집·육성 재미에 기여한다. 리스크는 §9-3(전령 반복 회복)·§9-4(징집병 다수 승급 시 풀 반복 충전)가 의도된 설계인지 사용자 확인이 없다는 점. 유지 시에도 §7처럼 회귀 테스트가 없어 실수로 깨질 수 있다 |
