# 병렬 개발 운영

## 역할과 작업 공간

| 담당 | 환경 | 책임 |
|---|---|---|
| 메인 개발자 | Codex, 원본 프로젝트의 `codex/integration` 브랜치 | 설계, 작업 배정, 파일 소유권, 리뷰, 순차 통합, 최종 검증 |
| 서브 개발자 1 | ZCode / GLM-5.3-Flash, `.worktrees/zcode-<작업ID>` | 배정 범위 구현·테스트·인계 |
| 서브 개발자 2 | Antigravity / Gemini, `.worktrees/antigravity-<작업ID>` | 배정 범위 구현·테스트·인계 |
| 사용자 | 기획 및 최종 확인 | 게임 규칙 결정, 결과 확인, main 반영 결정 |

모델별 실력을 가정해 담당 영역을 고정하지 않는다. 독립적으로 끝낼 수 있는 작업을 파일 단위로 나눈다. 서브 AI가 상대방 변경을 기다려야 한다면 먼저 공통 인터페이스를 메인이 확정하고 커밋한다.

각 워크트리는 소스 파일이 독립적이지만 Git 저장소·브랜치·설정은 공유한다. Unity의 `Library`, `Temp`, `obj`, `Logs`, `UserSettings`는 공유하거나 링크하지 않는다. 워크트리는 Assets 밖의 `.worktrees`에 생성하며 Git에서 제외한다. 최초 Unity 실행에는 별도 임포트 시간과 디스크 공간이 필요하다.

## 시작 방법

1. 메인은 `BOARD.md`에서 작업과 파일 소유권을 기록한다. `TASK_TEMPLATE.md`를 복사해 `Docs/Parallel/Tasks/<작업ID>.md`를 만들고, 허용 파일·금지 파일·기준 버전·완료 조건을 채운다.
2. 관련 미커밋 변경을 먼저 검토한다. 작업에 필요한 변경은 별도 검토 커밋으로 기준에 포함하고, 무관한 변경은 원본에 보존한다. 미커밋 변경은 워크트리에 자동으로 전달되지 않는다.
3. 작업서와 공통 변경을 통합 브랜치에 커밋한 뒤, 그 커밋으로 워크트리를 만든다. 작업서는 `Ready` 상태여야 한다.
4. 각 앱에서 배정된 워크트리 폴더만 연다. `START_ZCODE.md` 또는 `START_ANTIGRAVITY.md`의 시작 지시문에 작업서 경로를 넣어 전달한다. 앱이 AGENTS.md를 자동으로 읽는다고 가정하지 않는다.
5. 메인은 상태와 인계서를 검토하고, 완료된 변경을 한 건씩 통합한다.

PowerShell 명령은 저장소 루트에서 실행한다. 스크립트 실행 정책에 막히면 해당 호출에만 `powershell -NoProfile -ExecutionPolicy Bypass -File ...` 형식을 사용한다. 시스템 전체 실행 정책은 변경하지 않는다.

```powershell
# 메인: 현황 확인
./Tools/Parallel/Team.ps1 -Action Status
# 메인: 작업마다 새 브랜치와 워크트리 생성. 기존 폴더는 덮어쓰지 않는다.
./Tools/Parallel/Team.ps1 -Action New -Agent zcode -Task m1-ap-feedback -Base HEAD
./Tools/Parallel/Team.ps1 -Action New -Agent antigravity -Task m1-result-ui -Base HEAD
```

도구 자체의 회귀 검증은 `./Tools/Parallel/Test-Team.ps1`로 실행한다. 별도 임시 Git 저장소에서 생성·격리·오류 차단·실행권을 확인하며 게임 코드는 실행하지 않는다. 검증용 임시 저장소는 결과 확인을 위해 보존하고 경로를 출력한다.

예시 작업명은 실행할 과제가 아니다. 현재 `bootstrap` 워크트리 둘은 연결 확인용 대기 공간이다. 첫 과제를 배정할 때 작업서를 포함한 새 워크트리를 만들고 앱에서 새 폴더를 연다. 기존 폴더나 브랜치는 자동으로 삭제하지 않는다.

## 파일 소유권과 인계

- 작업 상태: `Draft` → `Ready` → `InProgress` → `Review` → `Integrated` → `Verified`. 진행 불가 시 `Blocked`와 이유를 기록한다.
- `BOARD.md`, 운영 규칙, 마일스톤 갱신은 메인만 담당한다. 서브 AI는 자신의 작업서 및 인계서만 갱신한다. 다른 워크트리에서 보드가 실시간 갱신되지는 않으므로 새 지시는 메인이 명시적으로 전달한다.
- 작업서에 허용한 파일만 편집한다. 폴더를 허용할 경우 그 폴더 전체를 한 AI가 소유한다. `.meta`도 동일 소유권에 포함한다.
- `BattleManager.cs`, `ActionRuntimeController.cs`, 공통 인터페이스, `.asmdef`, 패키지, 씬·프리팹은 충돌 위험이 높다. 필요한 경우 메인이 한 AI에게만 명시적으로 배정한다.
- 범위를 벗어난 수정이 필요하면 이유와 최소 변경안을 인계서 또는 응답으로 전달한다. 메인이 작업서를 변경하기 전에는 해당 수정을 진행하지 않는다.
- 서브 AI는 `HANDOFF_TEMPLATE.md`를 사용해 `Docs/Parallel/Handoffs/<작업ID>.md`에 결과를 기록하고, 허용 파일만 명시적으로 스테이징해 자신의 브랜치에 커밋한다. 무조건적인 `git add .`는 피한다.
- 최종 응답에는 코드 커밋 해시와 최종 브랜치 HEAD, 인계서 경로를 적는다. 인계서 자체의 커밋 해시를 같은 파일에 재귀적으로 기록하지 않는다.
- Unity를 실행할 수 없었다면 `Review / Unity 검증 대기`로 제출할 수 있다. 미검증을 성공으로 표시하지 않는다.

## Unity 실행권

코드 편집은 병렬로 수행하되 Unity 에디터 조작, 배치 컴파일, Test Runner, Play Mode 검증은 프로젝트 팀 전체에서 한 번에 한 작업만 수행한다. 기본 담당은 메인이다. 다른 앱에서 시작한 Unity도 확인한다.

```powershell
# 검증할 워크트리에서 실행하고 반환된 token을 보관
./Tools/Parallel/Team.ps1 -Action AcquireUnity
# 컴파일, 테스트, Play Mode 검증 후 Play Mode를 종료하고 진행 중 배치 작업도 종료 확인
./Tools/Parallel/Team.ps1 -Action ReleaseUnity -Token '<반환된 token>'
```

실행권은 공유 Git 디렉터리의 `parallel-team/unity-lease.json`에 원자적으로 생성한다. 이는 협업 규칙이며 Unity 프로세스를 강제로 차단하는 장치는 아니다. MCP 연결 시 에디터의 프로젝트 절대 경로를 반드시 확인한다. 원본 에디터의 로그로 서브 워크트리 검증을 대신하지 않는다.

시간 경과만으로 실행권을 빼앗지 않는다. 비정상 종료로 남은 실행권은 메인이 소유자와 실행 중 Unity 작업을 확인한 후 복구한다. 정상 반납은 소유 워크트리와 토큰이 모두 일치해야 한다.

## 리뷰와 통합

1. 메인은 작업서의 기준 커밋부터 서브 브랜치 HEAD까지 diff·커밋 목록을 읽고 허용 파일, 직렬화 영향, 테스트 근거를 확인한다. 미커밋 파일이 남았다면 완료된 결과와 구분한다.
2. 통합 전 원본의 미커밋 변경을 확인한다. 미커밋 변경이 남아 있으면 해당 원본에서 통합하지 말고, 깨끗한 별도 통합 검증 워크트리를 사용하거나 사용자 변경을 먼저 검토·보존한다. 자동 stash/reset은 하지 않는다.
3. 깨끗한 `codex/integration` 또는 `codex/integration-<작업ID>` 브랜치에서 검토한 정확한 커밋을 순서대로 `git cherry-pick <SHA>` 한다. 범위가 명확하지 않은 일괄 병합은 하지 않는다. `main`에서는 통합하지 않는다.
4. 충돌은 메인이 원인을 검토해 해결한다. 이해가 부족하면 해당 서브 AI에게 수정을 요청한다. 전체 파일에 ours/theirs를 무조건 적용하지 않는다.
5. 통합된 결과에서 컴파일, 관련 Edit Mode 테스트 및 필요한 정식 경로 Play Mode 검증을 수행한다. 두 변경을 함께 적용한 상태의 검증이 최종 기준이다.
6. 검증 결과를 기록하고 보드 상태를 갱신한다. `main` 반영·원격 push·브랜치 및 워크트리 삭제는 자동 수행하지 않는다.

## 앱 간 전달 범위

이 시스템은 Git 워크트리와 문서로 연결한다. ZCode와 Antigravity를 자동 호출하는 API나 CLI 연결은 구성하지 않았다. 현재는 사용자가 각 앱에서 지정 폴더를 열고 시작 지시문을 전달한다. 이후 메인은 같은 저장소의 서브 브랜치·인계서·변경 파일을 직접 읽어 리뷰할 수 있다. 자동 호출은 해당 앱의 실제 지원 방식과 사용자 설정을 확인한 뒤 추가한다.
