# Checkmate RPG — 프로젝트 가이드라인 및 JEV 검사 기준

문서 기준일: **2026-09-20**

대상: 메인 개발자, 병렬 개발 AI, 프로젝트를 검사하는 JEV 및 리뷰어.

이 문서는 구현·데이터·UI·아트 결과물을 판단하는 **검사 기준**이다. 현재 프로젝트 전체가 기준을 충족한다는 완료 보고가 아니다. JEV의 특정 제품이나 도구 권한을 가정하지 않는다. 확인할 수 없는 항목은 미검증으로 남기며, 검사 요청을 자동 수정·삭제·병합·외부 전송의 허가로 해석하지 않는다.

## 1. 프로젝트 정체성과 기준의 우선순위

### 보존해야 하는 방향

- 체스 기물의 이동·위치 선정과 AP 기반 실시간 전술을 결합한 RPG다.
- 명일방주를 의식한 서브컬처 방향성, 캐릭터 편성·육성·스킬 선택과 아웃게임 경험은 사용자가 유지하기로 한 핵심 의도다.
- 레벨업·스킬·기보·칙령 등은 관련 기획과 구현을 대조하여 검사한다. 일반적인 체스 게임에 불필요하다는 이유로 제거하지 않는다.
- 기능 수보다 이동, 공격, 자원 사용, 예측과 피드백의 일관성을 우선한다.
- 정상 작동하는 시스템을 재사용하고, 변경은 요청한 목적에 집중한다. 문제 제안에는 플레이어 영향과 최소 수정안을 함께 적는다.

### 지시·기획·구현의 구분

작업 지시는 **최신 사용자 명시 지시 → [AGENTS.md](AGENTS.md) → 승인된 작업서 및 관련 기획 → 이 README → 과거 참고 문서** 순으로 확인한다. 하위 문서가 상위 지시를 뒤집을 수 없다.

| 질문 | 판단 근거 |
|---|---|
| 어떻게 동작해야 하는가? | 최신 사용자 결정, 승인된 기획과 작업서 |
| 지금 어떻게 동작하는가? | 현재 코드, 에셋 직렬화 값, 실제 실행 결과 |
| 검증되었는가? | 해당 버전에서 수행한 테스트·로그·관찰 기록 |

코드에 값이 존재한다고 기획 확정값으로 간주하지 않는다. 문서의 “완료”도 실행 증거를 대신하지 않는다. 불일치는 버그, 문서 노후화, 기획 결정 필요 중 무엇인지 근거와 함께 분류한다.

### 먼저 읽을 문서

## 2. 환경과 프로젝트 구조

문서 작성 시 [ProjectVersion.txt](ProjectSettings/ProjectVersion.txt)는 **Unity 6000.3.10f1**을 지정한다. 렌더 파이프라인은 **URP**이며 [manifest.json](Packages/manifest.json)에 Universal RP 17.3.0이 선언되어 있다. 이후 검사에서는 이 문장보다 실제 파일을 다시 확인한다.

- PC 대상 프로젝트다. 다른 Unity 버전으로 자동 업그레이드하지 않는다.
- 지시문에 HDRP·UE5가 등장해도 프로젝트의 파이프라인 변경 근거가 되지 않는다.
- 설치 버전, 열려 있는 프로젝트 절대 경로, 브랜치, 패키지 잠금 파일을 확인한다.
- 의존성 선언만으로 임포트·컴파일 성공을 판정하지 않는다.

정식 경로는 [OutgameScene](Assets/Scenes/OutgameScene.unity) → 스테이지 선택·덱 편성 → [BattleScene](Assets/Scenes/Test/BattleScene.unity) → 결과·보상·아웃게임 복귀다. [CombatSandbox](Assets/Scenes/CombatSandbox.unity)는 전투 분리 검증용이며 저장·씬 전환까지 포함한 정식 경로 검증을 대신하지 않는다.

| 경로 | 책임과 검사 초점 |

위 표는 탐색 안내다. 예상 경로와 다르다는 이유로 파일을 일괄 재배치하지 않는다.

## 3. JEV 검사 절차와 판정 체계

### 검사 시작

1. 요청 범위와 수정 권한을 확인한다. 검토만 요청되었으면 읽기·분석에 한정한다.
2. `git status --short`, 브랜치, HEAD, 워크트리 절대 경로를 기록한다.
3. 기존 미커밋 변경과 검사 대상을 구분한다. 미추적 파일도 사용자 작업일 수 있다.
4. 적용되는 AGENTS와 작업서를 읽는다.
5. 관련 호출자·데이터·테스트를 함께 추적한다. 주석 하나로 결론 내리지 않는다.
6. 실행 검증에는 Unity 실행권과 연결 프로젝트 확인이 선행한다.
7. 문제마다 기대/실제 결과, 재현 조건, 근거, 영향과 최소 수정안을 기록한다.

### 항목 상태

| 상태 | 사용 조건 |
|---|---|
| `PASS` | 지정한 범위·조건에서 충족을 증거로 확인 |
| `FAIL` | 기준 위반 또는 실제 결함 확인 |
| `UNVERIFIED` | 도구 제한, 자료 부족, 버전 불일치 등으로 확인하지 못함 |
| `N/A` | 적용되지 않음. 이유 필수 |
| `DECISION REQUIRED` | 기대 동작·수치 미확정 또는 상위 지시 충돌 |

필수 항목에 FAIL이 있으면 **수정 필요**, 필수 미검증·미결정이 남으면 **검증 보류**, 필수 항목을 모두 충족하면 **검사 범위 내 통과**로 보고한다. 부분 검사로 프로젝트 전체를 통과 처리하지 않는다.

| 우선도 | 영향 예시 |
|---|---|
| P0 치명적 | 저장 소실, 진행 불가, 반복 크래시, 사용자 작업 파괴 |
| P1 높음 | 핵심 전투 불일치, 중복 보상, 실제 상태를 바꾸는 예측, 필수 화면 접근 불가 |
| P2 보통 | 특정 조건의 입력·표시 결함, 부분적인 UV 밀도·패딩 결함 |
| P3 낮음 | 진행에 영향 없는 표현·정렬·문서 개선 |

심각도는 실제 영향과 발생 조건으로 정한다. 미검증을 재현된 버그처럼 표현하지 않는다.

### 증거 요건

- 코드: 경로, 심볼, 현재 줄 번호 및 관련 호출 흐름.
- 에셋: 경로/GUID, 직렬화 값, 씬·프리팹의 실제 참조.
- 실행: 날짜, 버전·커밋·미커밋 여부, 씬, 재현 절차, 기대/실제 결과, 로그.
- 테스트: 어셈블리·필터, 실행/성공/실패/제외 수, 결과 파일.
- 이미지: 실제 에디터 캡처 또는 실제 데이터로 그린 도표. 컨셉 이미지로 검증을 대신하지 않는다.
- 비교 수치: 전후 해상도·스케일·정규화 기준. 서로 다른 분모의 값을 동일 조건처럼 비교하지 않는다.

## 4. 전투 아키텍처 검사

### 기존 행동 처리 경로

대표 탐색 시작점은 `BattleManager` → `UnitBrain` → [ActionRuntimeController](Assets/Scripts/Core/ActionRuntimeController.cs)의 접수 → 스케줄러·해석 → 런타임 뮤테이션 커밋이다. 세부 순서와 예외는 현재 소스로 확인한다.

- 기존 경로를 우회하는 피해·이동·상태 부여 로직을 별도로 추가하지 않는다.
- 시뮬레이션과 컴포넌트 동기화 책임을 확인한다. Transform만 이동하고 점유·런타임 위치를 남겨두면 안 된다.
- 접수, AP/SP 예약, 해석, 실패·취소, 환불·해제를 각각 검사한다.
- 이벤트와 연출이 동일 피해나 보상을 다시 적용하지 않는지 확인한다.
- 일반 이동과 넉백·당기기 등 강제 이동을 구분한다.
- 격자 밖 이동, 중복 점유, 사망 대상의 예약 행동, 전투 종료 후 입력을 검사한다.

### 예측·실전·리플레이

- 예측은 복제 상태만 변경한다. 실제 HP/AP/SP, 이벤트, 저장 데이터에 영향이 있으면 FAIL이다.
- 동일 조건은 공유 규칙으로 판정한다. 경로마다 복사한 수식은 불일치 위험으로 검토한다.
- 새 상태는 복제·스냅샷·기록·복원까지 추적한다.
- 논리 틱과 프레임 시간을 혼합하지 않는다. 정렬·동률·난수의 재현성도 검사한다.
- 리플레이 검증이 최종 상태인지 중간 이벤트까지인지 명시한다. 과거 결정성 테스트 기록만으로 현재를 보증하지 않는다.

### 이동 직후 공격 유예

사용자 의도는 움직이는 적 때문에 유효하게 시작한 공격이 지나치게 빗나가는 문제를 완화하는 것이다. 근접/원거리는 기존 공격 타입으로 구분하며 외형·기물 이름으로 추정하지 않는다.

[AttackGraceRules](Assets/Scripts/Core/AttackGraceRules.cs)와 호출부를 함께 검사한다. 현재 소스의 정상 이동 기록, 공격 접수 시점, 공격자 이동 여부 및 유예 틱을 확인한다.

필수 사례는 현재 위치에서 정상 타격, 접수 후 대상 이동, 유예 안/밖, 같은 틱 경계, 공격자 이동, 강제 이동, 대상 사망, 연속 이동, 경로 장애물이다. 근접/원거리와 예측·실전 결과도 비교한다.

컨트롤러의 유예 값은 소스에 **시험값·기획 미확정**으로 표시되어 있다. 기본값을 최종 밸런스로 고정하지 않는다. 유예 구현을 위해 과거 위치에 실제 유닛이나 충돌 메시를 복제하지 않는다.

### AI·물리·상태 효과

- AP 비용·회복·행동 간격을 함께 검사한다. 적 킹 추격 문제를 단일 비용 탓으로 단정하지 않는다.
- AI 왕복 이동, 안전지대 공격, 한 전략 독점, 지나친 대기는 플레이테스트 항목으로 기록한다.
- 넉백/Splat/지형 효과는 기존 경로를 재사용한다. 데모에서만 다른 공식을 쓰지 않는다.
- 상태 효과의 상한, 갱신/교체, 지속 시간, 틱 발생, 제거·사망·중첩 순서를 확인한다.
- 순수 모델 테스트 통과와 실제 컴포넌트·게임 루프 검증을 구분한다.

## 5. 아웃게임·성장·저장 검사

### 데이터와 UI 책임

- UI는 기존 서비스의 결과를 표시한다. 버튼마다 비용·스탯 공식을 별도 구현하지 않는다.
- 캐릭터 식별자, 표시 이름, 에셋 이름, 저장 키를 혼동하지 않는다. 이름 변경 시 저장 호환성을 확인한다.
- 레벨업·승급·스킬·기보·칙령의 조건·비용·효과는 기획과 실제 데이터에서 추적한다.
- 편성과 스킬 선택이 전투 입장 후 실제 반영되는지 확인한다.
- 승급 시 AP 전량 회복 같은 효과를 확정 기획으로 가정하지 않는다. 근거 없는 추가·삭제 모두 피한다.

### 저장·보상 안전성

[SaveManager](Assets/Scripts/Progression/SaveManager.cs)는 `Application.persistentDataPath`의 `saveData.json`과 백업·임시 파일을 다룬다. 테스트용 경로·데이터를 우선 사용하며 실제 사용자 저장을 초기화하지 않는다.

| 검사 | 기대 조건 |
|---|---|
| 저장 실패 | 감지 가능하고 기존 정상 데이터 보존 |
| 본체 손상 | 복구 경로와 손상 파일 보존 확인 |
| 구버전·누락 필드 | 필요한 기본값/이행과 기존 소유·진행 정보 유지 |
| 재실행 | 성장·편성·해금·보상 복원 |
| 연속 클릭 | 음수 재화나 의도치 않은 중복 구매 방지 |
| 결과 재진입 | 동일 전투의 중복 지급 방지 |
| 정상 재도전 | 새로운 전투의 반복 보상은 기획대로 지급 |

[BattleRewardService](Assets/Scripts/Progression/BattleRewardService.cs)의 첫 클리어 보너스 중복 방지와 **같은 전투의 반복 보상 중복 방지**는 다르다. 첫 클리어 기록만 보고 전체 지급이 안전하다고 판단하지 말고 호출자와 종료 상태도 검사한다.

경제 수치·해금 순서·돌파 방식이 미확정이면 결정 필요로 남긴다. 검사 편의를 위해 새로운 경제 모델을 도입하지 않는다.

## 6. C# 및 Unity 컨벤션

### 코드 형식

- 새 코드는 주변 형식을 따른다. 일반적인 형태는 4칸 들여쓰기, 중괄호 줄 분리, `CheckmateRPG.<영역>` 네임스페이스다.
- 타입·메서드·프로퍼티는 PascalCase, 매개변수·지역 변수는 camelCase를 기본으로 한다. private 필드 접두사는 기존 파일 관례를 따른다.
- 직렬화 필드는 포맷 통일 목적으로 이름을 바꾸지 않는다.
- 주석은 제약·이유·단위·경계 조건을 설명한다. 실제 동작과 다른 주석을 방치하지 않는다.
- 기존 대형 클래스가 있다는 이유로 요청 밖 분해·이동·일괄 포맷을 수행하지 않는다.

### 직렬화·참조·어셈블리

- `.meta`와 GUID를 보존한다. 에셋 이동 시 함께 이동하고 기존 `.meta`를 재생성하지 않는다.
- 필드 이름·타입 변경 시 `FormerlySerializedAs` 등 적절한 이행과 실제 에셋 값을 검증한다.
- 공유 ScriptableObject의 설계 데이터와 런타임 가변 상태를 분리한다.
- Missing Script, 누락 참조, 의도하지 않은 프리팹 override를 확인한다.
- 런타임에 `UnityEditor` 의존성을 추가하지 않고 `.asmdef` 경계를 존중한다.
- 씬·프리팹·ProjectSettings·패키지는 해당 작업에 필요한 경우만 수정한다.
- 생성 도구는 덮어쓰기 범위를 먼저 확인하고 재실행 시 중복 생성 여부를 검사한다.
- `Library/`, `Temp/`, `obj/` 등 생성 파일을 구현 대상으로 편집하지 않는다.

### 생명주기와 성능

- 불필요한 `Update()` 대신 기존 이벤트·틱 흐름을 우선한다.
- 반복 경로의 LINQ·임시 컬렉션·문자열·전체 탐색 비용을 확인한다. 근거 없이 전면 금지하거나 풀링을 추가하지 않는다.
- 이벤트 해제, 지연 작업 중단, 씬 전환 후 참조 수명을 확인한다.
- 영속 객체가 중복 생성되거나 이전 전투를 참조하지 않는지 검사한다.
- 예외를 빈 catch로 숨기지 않는다. 사용자 피드백과 진단 로그를 구분한다.
- 성능 수치는 환경·장면·해상도와 함께 보고한다. 임의 FPS·메모리 목표를 만들지 않는다.

## 8. Blender·유적 모듈·UV 컨벤션

### 최신 원칙과 작업 범위

[기존 UV 기록](Docs/RuinUVRules.md)의 “급경사 모두 분리”와 하드 에지 중심 분할은 이후 사용자가 지시한 **연속 스트립 우선 원칙으로 대체된 부분**이다. 과거 PASS나 파일명 `verified`를 현재 승인 근거로 삼지 않는다.

- UV 작업에 메시 추가, 면 분할, 토폴로지·크기·배치 변경을 포함하지 않는다.
- 현재 Blender 상태를 확인하고 백업본을 만든다. 저장 전 화면 상태와 디스크 파일의 차이를 확인한다.
- 오브젝트, 정점·에지·면, 좌표, 변환, 재질 슬롯, 모디파이어, 노멀 관련 상태를 전후 비교한다.
- 허용 범위는 UV와 필요한 seam이다. 다른 변경이 필요하면 근거를 먼저 제시한다.
- 덩굴은 Unity에서 작업한다. UV 작업에 덩굴·잎·장식을 새로 만들지 않는다.
- 바위와 녹슨 금속의 무드는 사용자 레퍼런스를 따른다. UV만 요청되면 재질까지 바꾸지 않는다.

### seam·연속성

- UV seam을 sharp edge와 동일시하지 않는다.
- 여러 90도 코너가 있어도 연속 건축 밴드는 가능한 한 하나의 스트립으로 유지한다.
- 새 seam·아일랜드에 높은 비용을 부여한다. 왜곡 최소화를 이유로 면마다 분리하지 않는다.
- 계단의 디딤판·라이저·측면은 토폴로지가 허용하는 범위에서 긴 연속 구조로 정리한다.
- 몰딩은 모든 profile edge를 자르지 않고 둘레를 여는 최소 절개를 우선한다.
- 베벨은 특별한 이유가 없으면 인접 주 면에 붙인다. 작은 coplanar/near-coplanar 면을 독립시키지 않는다.
- 분리된 메시를 UV 연속성 때문에 용접하지 않는다. 불가피한 독립 면은 원인을 기록한다.
- 베이크 위험은 해당 경계와 실제 결과로 판단한다. 무작정 분할하거나 근거 없이 안전하다고 주장하지 않는다.

### 직교 정리

1. 실제 직선 루프와 주 방향을 U/V축에 맞춘다.
2. 같은 역할의 패널·계단·몰딩·스트립 방향을 통일한다.
3. 규칙적인 곡면 쿼드도 dominant loop를 기준으로 정리한다.
4. 폭 변화·테이퍼·오목/볼록 경계는 유지한다. 완벽한 직사각형을 강제하지 않는다.
5. 변형이 크게 늘면 직교보다 낮은 왜곡을 우선한다.
6. 방사형·유기적·불규칙 구조는 억지로 직선화하지 않는다.
7. 정렬만을 위해 추가 seam을 만들지 않는다.
8. 기준 축·에지를 유지하며 국부 relax를 수행한다.
9. 실제 면적 기준으로 밀도를 다시 계산한다.
10. 방향과 패딩을 유지해 패킹한다. 임의 회전으로 정리 결과를 무효화하지 않는다.

### 실제 표면 면적과 텍셀 밀도

**아일랜드 평균만 맞추는 것으로는 통과할 수 없다.** Path처럼 한 아일랜드 안에서도 실제 작은 면이 과도한 UV 면적을 차지할 수 있다.

정사각형 텍스처 해상도 R, 월드 스케일을 반영한 면적 A_world, 정규화 UV 면적 A_uv에 대해:

```text
TD(px / world-unit) = R × sqrt(A_uv / A_world)
```

- 대응하는 삼각형으로 측정한다. 측정용 계산이 실제 메시 변경을 허용하는 것은 아니다.
- 비균일 오브젝트 스케일과 모델 단위를 반영한다. 로컬 면적만으로 실면적이라고 보고하지 않는다.
- 면/삼각형별, 아일랜드별 밀도와 전체 기준 대비 편차를 기록한다.
- 같은 면적 비율이어도 방향별 늘어남은 가능하다. 체커와 길이 방향 변형도 확인한다.
- 같은 외장 역할은 ±5%를 검사 목표로 삼고 숨은 면 축소 같은 예외는 명시한다.
- 공통 절대 TD는 실제 사용 크기·해상도와 함께 확정한다. 미정이면 임의 px/m 기준을 만들지 않는다.
- 전후 각각의 평균 또는 같은 절대 목표 중 어떤 기준인지 명시한다. 서로 다른 분모를 혼용하지 않는다.

### 패킹·아틀라스·베이크

| 해상도 | 아일랜드 간 최소 여백 | 권장 여백 |
|---|---:|---:|
| 1024 | 4px | 8px |
| 2048 | 8px | 16px |
| 4096 | 16px | 32px |

이는 검사 출발점이며 모든 밉 단계에서의 안전 보장이 아니다. 타일 외곽 여백은 별도 기록하고 작업 지정값을 따른다. 미지정이면 선택한 값을 명시하여 기준을 확정한다.

- 최종 UV는 지정 0~1 또는 UDIM 내부에 둔다. 의도하지 않은 중첩·면적 0·뒤집힘을 검사한다.
- 충전율은 실제 점유 면적으로 측정한다. 바운딩 박스 합이나 중복 스택 면적을 사용하지 않는다.
- 70~85%는 패킹 검토 목표다. 연속성·패딩·밀도를 희생하지 않는다. 낮은 효율은 원인과 대안을 기록한다.
- 공통 아틀라스는 같은 재질 세트, 호환 TD, 같은 목표 해상도일 때만 검토한다.
- 독립 스트리밍·독립 모듈 재사용·다른 재질이나 TD 요구가 있으면 합치지 않는다.
- 보완적인 아일랜드 모양을 조합하되 메시 오브젝트까지 합칠 필요는 없다.
- 스택/미러 사용 시 베이크 제외·오프셋 절차를 명시하고 베이크 UV와 최종 UV를 구분한다.
- 내보내기 도구가 실제 사용하는 채널을 확인한다. UVMap/BakeUV/UV_Runtime이라는 이름만으로 판단하지 않는다.
- 베이크·최종 셰이딩 미검증 상태를 `BAKE READY` 또는 Unity 적용 완료로 보고하지 않는다.

제출물에는 작업본·백업 경로, 실제 UV 이미지, 면·아일랜드 수, 형상 보존 비교, TD 분포, 패딩·경계·중첩·충전율과 예외를 포함한다. 최종 카메라의 seam 노출과 Unity 결과가 미확인이면 별도 미검증으로 남긴다.

## 9. Git·병렬 개발·도구 사용

- 단일 목적의 변경만 수행하고 기존 미커밋 작업을 되돌리지 않는다.
- 승인 없는 대량 삭제, `git reset --hard`, `git clean` 등 일괄 폐기를 하지 않는다.
- `main` 자동 병합·이력 재작성을 하지 않는다. push·공유·정리도 해당 권한을 확인한다.
- `.meta`를 포함한 허용 파일만 수정·스테이징한다. 무조건적인 `git add .`를 피한다.
- Codex는 분할·공통 인터페이스·리뷰·통합·최종 검증을 담당한다.
- ZCode·Antigravity는 자기 워크트리의 `Ready` 작업서 범위만 구현한다.
- 동일 파일 동시 편집을 피한다. 공통 API·씬·프리팹·패키지·어셈블리는 담당을 명확히 한다.
- 상태는 `Draft → Ready → InProgress → Review → Integrated → Verified`다. 구현과 통합 검증 완료를 구분한다.
- 자동 호출 연결·인증 상태는 실제 설정·실행으로 확인한다. 과거 문서만으로 연결을 가정하지 않는다.
- 비밀 값, 인증 URL, 실제 사용자 저장 내용은 보고서에 노출하지 않는다.

Unity 조작·배치 테스트는 공용 실행권을 획득하고 한 작업씩 수행한다. [Team.ps1](Tools/Parallel/Team.ps1)의 지원 형식:

```powershell
./Tools/Parallel/Team.ps1 -Action Status
./Tools/Parallel/Team.ps1 -Action AcquireUnity
# 검증 후 Play Mode와 배치 작업 종료를 확인하고 반납
./Tools/Parallel/Team.ps1 -Action ReleaseUnity -Token '<반환된 token>'
```

실행권은 프로세스 강제 차단 장치가 아니다. 에디터 실행 여부와 연결 프로젝트 절대 경로를 따로 확인한다. 시간 경과만으로 실행권을 빼앗지 않는다.

### 컴파일과 테스트

- 같은 프로젝트의 에디터가 열린 상태에서 별도 배치 Unity를 실행하지 않는다.
- 종료 코드와 관련 전체 로그를 확인한다. 오류 문자열 검색만으로 성공을 단정하지 않는다.
- Edit Mode 어셈블리는 [CheckmateRPG.Tests](Assets/Scripts/Testing/EditModeTests/CheckmateRPG.Tests.asmdef)다. 관련 테스트와 결과를 기록한다.
- 규칙 변경·버그에는 필요한 회귀를 추가하되 문서 변경용 테스트는 만들지 않는다.
- 컴파일 실패는 수정 후 최대 3회 재검증한다. 해결되지 않으면 변경을 보존하고 원인·미검증 범위를 보고한다.

### Play Mode

1. 목적에 맞는 정식 경로 또는 샌드박스를 연다.
2. 시작 시 콘솔과 컴파일 상태를 확인한다.
3. 성공·실패·반복 입력과 기대 피드백을 확인한다.
4. 필요한 경우 승패·재시작·복귀·저장 복원을 확인한다.
5. 테스트 중과 종료 후 런타임 예외를 확인한다.
6. **성공·실패·중단 여부와 관계없이 Play Mode 종료를 확인한다.**

통과 기준은 관련 컴파일 오류·런타임 예외 0건, 관련 테스트 통과, 기대 동작 확인이다. 기존 오류는 새 오류와 구분하되 검증을 막으면 통과 처리하지 않는다. 경고도 원인·영향을 분류하며 무조건 숨기지 않는다.

문서만 변경했다면 내용·경로·범위를 검증하고 Unity 테스트 생략을 명시한다. 검증할 수 없는 항목은 성공으로 바꾸지 않고 사용자가 확인할 최소 절차를 안내한다.

## 12. 최종 제출 체크리스트

- [ ] 최신 지시와 실제 대상 버전을 확인했다.
- [ ] 기존 사용자 변경과 이번 변경을 구분·보존했다.
- [ ] 설계 의도, 구현 사실, 추정, 미검증을 구분했다.
- [ ] 문제에 근거·재현 조건·영향·최소 수정안을 첨부했다.
- [ ] 실행하지 않은 검증을 통과로 기록하지 않았다.
- [ ] 수치·밸런스·성능 목표를 임의 확정하지 않았다.
- [ ] 예측/실전/저장 또는 UV/내보내기 등 연결 경로를 확인했다.
- [ ] 범위를 넘는 수정·삭제·병합을 수행하지 않았다.
- [ ] 사용한 도구 종료와 필요한 실행권 반납을 확인했다.
- [ ] 변경 내용, 검증 결과, 남은 확인을 한국어로 전달했다.

문서 갱신 시 새로운 사용자 결정과 확인한 구현 근거를 반영한다. 상세 진행 상태와 실행 증빙은 개별 작업서·인계서에 남기며 과거 결과를 현재 완료 상태로 옮겨 적지 않는다.
